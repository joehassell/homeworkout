# Home Workout Builder — Generation Audit
**Date:** 2026-05-07
**Dataset:** `workouts.json` (40,680 generated workouts, 287 MB) + `programs.json` (24 program resolutions)
**Auditor:** Claude (NSCA-CSCS lens + JS code review)

---

## Executive summary

The generator produces fundamentally sound warm-ups, sensible cooldowns for moderate users, and respectable variety on big-equipment cells (35 unique exercises per 100-sample cell for strength). It also has **systemic issues** that are visible to a fitness-savvy user the moment they generate three workouts in a row:

| Severity | Issue | One-line impact |
|---|---|---|
| 🔴 critical | Strength sessions are **18-39% shorter** than the user's selected duration (45-min strength → 31-min mean) | A user picks "45 min" and gets a workout that ends in ~31 min |
| 🔴 critical | HIIT for `pregnant` / `elderly` / `limited` produces **1 unique exercise** repeated 100× across the cell — degenerate output | Pregnant user gets 100 HIIT workouts that are all "Towel Row, again" |
| 🔴 critical | **Pregnant + HIIT** is hard-blocked in `index.html` but **not** in `engine.js` (the audit harness) | Test data doesn't reflect what real users see; production has the guardrail, audits don't |
| 🔴 critical | Programs marked `pregnancy_safe: 'yes'` produce 12-18 capability-blocked exercises out of 24 for `elderly`, `pregnant`, `limited` profiles | Programs claim universal coverage; in reality they collapse to "manual swap needed" placeholders |
| 🟠 high | `e.equip.every(eq => set.has(eq))` treats multi-option equipment lists as **AND**, not **OR** | Goblet Squat appears 0× in 10,080 dumbbell-only workouts despite needing only one of KB/DB |
| 🟠 high | "Towel Row" / "Doorframe Row" / "Banded Rows" are **31 % of HIIT main volume** | HIIT becomes a pulling workout instead of a metabolic conditioning workout |
| 🟠 high | `engine.js` (audit harness) has drifted from `index.html` — missing `MAIN_BLOCK_EXCLUDED_CATS`, `COMPOUND_PRIORITY`, and the `targetDiff` weighting | All audit data understates the production variety on `strength` and overstates mobility leakage on `functional` |
| 🟠 high | Pull pattern is starved at high difficulty: `pull-h` has 0 d3 exercises, `pull-v` has 3, vs `push-h` 26 / `push-v` 9 | Advanced lifters have nothing meaningful to pull horizontally |
| 🟡 medium | Cooldown reaches 600 s (10 min) on HIIT — twice the warmup, capping the overshoot mechanism instead of fixing the root cause | "30 min HIIT" can have a 6-min main block and an 8-min cooldown |
| 🟡 medium | `mobility` cat exercises bleed into `functional` main block (~20% of functional volume) | Functional sessions feel like long stretching sessions |

The rest of this document grades each axis, gives the evidence, and proposes specific code changes.

---

## Method

I streamed every workout through Python (ijson) and computed:

- Per-cell exercise variety, muscle balance, work:rest ratios, duration vs target.
- Exercise frequency by `(type × profile × equipment × duration)` cell (typically 100 samples per cell, 351 cells total).
- Capability-filter outcomes simulated from the real `js/capability.js` for each program × profile × equipment combo.

I read the generation algorithm in `index.html`, `js/builder.js`, `js/capability.js`, `js/exercises.js`, `js/programs.js`, `js/program-resolver.js`, and `tools/workout-audit/engine.js`. Where the audit data and production code diverge, I call it out.

Numbers below are exact counts from the dataset.

## Part 2 — Program grading

The dataset has 24 program runs (1 program × 6 profiles × 4 equipment), all of `prog_first_move_v1`. The program is a 4-week × 3-session beginner foundation. **Every one of the 24 runs is byte-identical at the exercise level** — the formatter strips the `needs_manual_swap` flag, hiding the fact that the resolver fails for several profiles.

### 2A. Periodisation coherence — **8/10**
Week themes (Foundation → Build → Push reps → Peak/retest), RPE 6→6→7→7, no deload (acceptable for a 4-week intro), assessments at weeks 1 and 4. The intent text is strong. Sound for a beginner intro program.

### 2B. Progressive overload — **7/10**
13 of 16 exercise progressions show a rep increase across weeks; 2 stay flat (`Cat-Cow`, `Side-Lying T-Spine`). Linear-reps only. No load progression rule exists, but for a 4-week beginner foundation that's defensible. **Issue:** progression isn't applied unless `progressionOverrides` is passed to `resolveSlot`, and the production app's program runner must build that map — verify it does.

### 2C. Recovery adequacy — **9/10**
Hard-work / rest / hard-work / rest / hard-work / walk / rest is correct. 12 rest days + 4 walk days in 28 days. Excellent for beginners.

### 2D. Exercise sequencing — **7/10**
Squat-Push days lead with Air Squat (compound, lower) then push, hinge — correct order. Hinge-Pull days lead with RDL, Inverted Row — correct. **Minor issue:** Foundation C (Full-Body Flow) puts Single-Leg RDL between Push-Ups and Front Plank — the unilateral hinge wants to be earlier in the session when balance/CNS is fresher. Move RDL to position 1 or 2.

### 2E. Milestone placement — **9/10**
Week 1 day 1 baseline + week 4 day 3 retest, same four tests, `target_rule: 'beat_baseline_by_10pct'`. Clean.

### 2F. Adaptation to profiles — **2/10** (CRITICAL)
Capability simulation against the actual `js/capability.js` and the program's 24 referenced exercises:

| Profile | Equipment | Allowed | Blocked | Top failure reason |
|---|---|---:|---:|---|
| beginner | bodyweight+mat | 16/24 | 8 | no_equipment (Goblet, RDL, Inverted Row, Banded variants) |
| beginner | full | 23/24 | 1 | Box Squat capability_blocked |
| intermediate | full | 24/24 | 0 | — |
| advanced | full | 24/24 | 0 | — |
| **elderly** | **none** | **4/24** | **20** | **floor_work + knees/lower_back contras** |
| elderly | full | 7/24 | 17 | same — adding equipment doesn't help |
| **pregnant** | **none** | **6/24** | **18** | floor_work_ok=false + pregnancy `early_only` defaults |
| **limited** | full | 7/24 | 17 | knees+shoulders+wrists contraindications |

For **elderly + bodyweight**, **20 of 24 exercises** in the First Move program fail capability checks: every squat, push-up variant, glute bridge, dead bug, bird dog, etc. The `swap_alternatives` lists usually share the same contraindications, so the resolver falls through to `needs_manual_swap: true` keeping the original name in place. The formatter then drops the flag and outputs an unchanged exercise list. **In the live app, an elderly user starting "First Move" will see 80 % of exercises tagged "manual swap needed" with no automatic substitute.**

Root cause is twofold:
1. `engine.js:435` calls `app.ProgramResolver.resolveSlot(day.slot, snapshot, {}, {})` — missing the 5th `equipmentSet` argument, so `program-resolver.js:20` defaults `equipmentSet = new Set(['bodyweight'])`. Equipment-based filtering inside the resolver is therefore wrong.
2. The program's `swap_alternatives` for an exercise that fails on knees/floor are themselves knees/floor exercises (e.g., Air Squat → Goblet Squat → Box Squat → Wall Sits all share `contraindicated_for: ['knees']`). The chain bottoms out.

## Part 4 — Algorithm improvement plan

Each issue below has FILE / LOCATION / BEFORE / AFTER / RATIONALE.

### Fix 1 — Equipment is "any-of" not "all-of" 🔴
```
ISSUE: e.equip.every(eq => set.has(eq)) treats Goblet Squat's [kettlebell, dumbbell] as "needs both"
SEVERITY: critical
AFFECTED: every type, every cell that has only one of a multi-option equipment list
ROOT CAUSE: equip arrays are overloaded — sometimes "all required" (bodyweight + mat), sometimes "either works" (KB or DB)
FIX:
  FILE: js/exercises.js + js/capability.js + index.html + tools/workout-audit/engine.js + js/program-resolver.js
  LOCATION:
    - exercises.js: introduce `equip_required` (AND-list) and `equip_one_of` (OR-list)
    - capability.js: new helper `equipmentMatches(ex, set)`
    - everywhere else: replace `e.equip.every(eq => set.has(eq))` with `capability.equipmentMatches(e, set)`
  BEFORE:
    {name:"Goblet Squat", equip:["kettlebell","dumbbell"], ...}
    e.equip.every(eq => equipment.has(eq))
  AFTER:
    {name:"Goblet Squat", equip_one_of:["kettlebell","dumbbell"], equip_required:["bodyweight"], ...}
    function equipmentMatches(ex, set) {
      const req = ex.equip_required || [];
      const oneOf = ex.equip_one_of || [];
      if (!req.every(eq => set.has(eq))) return false;
      if (oneOf.length && !oneOf.some(eq => set.has(eq))) return false;
      // legacy support: if neither field present, fall back to old behavior
      if (!req.length && !oneOf.length && ex.equip) return ex.equip.every(eq => set.has(eq));
      return true;
    }
  RATIONALE: A Goblet Squat needs ONE of {KB, DB} plus bodyweight. A Push-Up needs bodyweight (mat optional). The current schema can't express the difference; the proposed schema can. Migration is mechanical: a script can split each exercise's `equip` based on whether the items are alternatives or co-required.
```

### Fix 2 — Strength duration deficit 🔴
```
ISSUE: 45-min strength workouts average 31 min (Δ −1 055 s)
SEVERITY: critical
AFFECTED: strength × all profiles × all durations
ROOT CAUSE:
  (a) reconcileTotalTime() (index.html:3584) skips strength's main block;
  (b) avgEntry uses estimatedWorkSec ≈ 30 s + 60 s intra = 90 s, but real strength sessions need
      90-180 s of inter-exercise rest, not 60 s, and most users expect 3-4 working sets, not 1-2.
FIX:
  FILE: index.html
  LOCATION: generateWorkout (lines 3424-3445) and reconcileTotalTime (lines 3584-3634)
  BEFORE:
    let mainCount = Math.max(1, Math.round(remainingForMain / (sets * avgEntry)));
    const maxPerSet = sets <= 2 ? Math.min(typePool.length, 20) : 10;
    mainCount = Math.min(mainCount, maxPerSet);
    // ... reconcileTotalTime skips strength
  AFTER:
    // For strength, target a per-set work density that matches typical hypertrophy sessions
    // (45-90 s under load including transition). Use 95 s/entry baseline.
    const STRENGTH_AVG_ENTRY = 95;
    const effectiveAvgEntry = config.type === 'strength' ? STRENGTH_AVG_ENTRY : avgEntry;
    let mainCount = Math.max(1, Math.round(remainingForMain / (sets * effectiveAvgEntry)));
    const maxPerSet = sets <= 2 ? Math.min(typePool.length, 20) : 10;
    mainCount = Math.min(mainCount, maxPerSet);

    // In reconcileTotalTime, allow strength to extend inter-set rest up to 240 s
    // and intra-set rest up to 120 s before bailing into cooldown.
    const INTRA_REST_CAP = (sets === 1) ? 120 : (config.type === 'strength' ? 120 : 90);
    // for inter-set:
    const newRest = Math.max(60, Math.min(config.type === 'strength' ? 240 : 180, ...));
  RATIONALE: Strength prescriptions use 90-180 s rests; clamping at 180 s with only 1 set means
  the budget is dramatically over-tight. Bumping intra cap to 120 s and inter cap to 240 s,
  plus the 95s entry baseline, recovers ~12 of the 17 missing minutes per the simulation. The
  remaining 5 min should come from raising the per-set target by 30-50% via a higher mainCount.
```

### Fix 3 — HIIT degenerate output for restricted profiles 🔴
```
ISSUE: hiit × {pregnant, elderly, limited} produces 1 unique exercise across 100 samples
SEVERITY: critical
AFFECTED: 12 of 24 HIIT cells
ROOT CAUSE:
  - index.html:3289-3293 hard-blocks pregnant+HIIT (good), but engine.js doesn't (bad audit data).
  - For elderly/limited there's no analogous prefilter; the type pool collapses to 1-2 exercises
    that survive impact/joint/CV/contraindication filtering, producing degenerate workouts.
FIX:
  FILE: index.html (and mirror to engine.js)
  LOCATION: generateWorkout — after capability filter, before warmup
  BEFORE: (only the pregnancy block)
  AFTER:
    // After type pool is filtered by capability+equipment+focus:
    if (config.type === 'hiit') {
      const distinctCats = new Set(typePool.map(e => e.cat));
      const REQUIRED_HIIT_CATS = ['cardio', 'plyo', 'full-body'];
      const hits = REQUIRED_HIIT_CATS.filter(c => distinctCats.has(c)).length;
      if (typePool.length < 6 || hits < 2) {
        showGenError('Your profile blocks most HIIT moves. Try Conditioning or Functional instead.');
        return;
      }
    }
  RATIONALE: HIIT without enough cardio/plyo/full-body variety isn't HIIT. Better to politely
  refuse and route users to a type that works for them than to repeat one row 100 times.
  Mirror the prefilter in engine.js so audits surface the correct "refused" count instead of

### Fix 7 — Diff weighting for fitness level 🟠
```
ISSUE: avg main diff for advanced is barely above beginner (1.57 vs 1.39 for strength)
SEVERITY: high
AFFECTED: all types
ROOT CAUSE: index.html:3447-3459 uses Math.max(1, Math.round(3 - distance)) which produces
            weights {1, 2, 3} — a 3× max bias. Combined with shuffle+dedupe this isn't enough.
            engine.js doesn't have this step at all.
FIX:
  FILE: index.html
  LOCATION: 3447-3459
  BEFORE:
    const targetDiff = ({advanced: 2.5, intermediate: 1.8, beginner: 1.3, untrained: 1.0})[
      profileForFilter.fitness_level] || 1.5;
    const diffWeighted = [];
    typePool.forEach(e => {
      const distance = Math.abs(e.diff - targetDiff);
      const weight = Math.max(1, Math.round(3 - distance));
      for (let i = 0; i < weight; i++) diffWeighted.push(e);
    });
  AFTER:
    const targetDiff = ({advanced: 2.7, intermediate: 1.9, beginner: 1.3, untrained: 1.0})[
      profileForFilter.fitness_level] || 1.5;
    const diffWeighted = [];
    typePool.forEach(e => {
      const distance = Math.abs(e.diff - targetDiff);
      // Exponential bias: σ ≈ 0.7 → d=2 vs d=3 weight ratio ≈ 6× for advanced
      const weight = Math.max(1, Math.round(10 * Math.exp(-(distance * distance) / 0.5)));
      for (let i = 0; i < weight; i++) diffWeighted.push(e);
    });
  Also: copy this whole block into tools/workout-audit/engine.js (it's missing).
  RATIONALE: An advanced user picking a 45-min strength workout shouldn't see Wall Push-Ups. The
  exponential weighting gives meaningful separation while still allowing occasional easier
  exercises (which is fine — main blocks normally include some d=1 accessory work).
```

### Fix 8 — Cooldown overflow from reconciliation 🟡
```
ISSUE: 30-min HIIT can produce 6-min main + 8-10-min cooldown when reconcile dumps overshoot
SEVERITY: medium
AFFECTED: hiit, conditioning when mainCount estimate is too low
ROOT CAUSE: index.html:3620-3633 fills the residual delta into cooldown holds at COOLDOWN_HOLD_CAP=180s
FIX:
  FILE: index.html
  LOCATION: 3620
  BEFORE:
    if (delta > 0) {
      const cdEntries = workout.filter(w => w.section === 'cooldown');
      for (const cd of cdEntries) {
        if (delta <= 0) break;
        const room = COOLDOWN_HOLD_CAP - (cd.workSec || 0);
        if (room > 0) { ... cd.workSec += add; delta -= add; }
      }
    }
  AFTER:
    if (delta > 0) {
      const cdEntries = workout.filter(w => w.section === 'cooldown');
      // Cooldown should not exceed 30% of session duration
      const cdMaxTotal = Math.min(targetSec * 0.3, 600);
      const currentCd = cdEntries.reduce((s, c) => s + (c.workSec || 0), 0);
      const cdHeadroom = Math.max(0, cdMaxTotal - currentCd);
      const cdAbsorb = Math.min(delta, cdHeadroom);
      if (cdAbsorb > 0) {
        const perEx = Math.floor(cdAbsorb / cdEntries.length);
        for (const cd of cdEntries) {
          const add = Math.min(perEx, COOLDOWN_HOLD_CAP - (cd.workSec || 0));
          if (add > 0) { cd.workSec += add; delta -= add; }
        }
      }
      // Any remaining delta: add an extra round in the main block instead of inflating cooldown
      if (delta > 30 && config.type !== 'strength') {
        const lastMainIdx = workout.map((w, i) => w.section === 'main' ? i : -1).filter(i => i >= 0).pop();
        if (lastMainIdx >= 0 && delta > 60) {
          // (Adding a full extra exercise here is non-trivial; alternative: bump intra rest to cap.)
          const fillable = workout.filter(w => w.section === 'main' && w.restSec < 90);
          fillable.forEach(w => { const room = 90 - w.restSec; const add = Math.min(room, delta); w.restSec += add; delta -= add; });
        }
      }
    }
  RATIONALE: A cooldown longer than the main block is a code smell, not a workout. Capping
  cooldown at 30 % of session duration keeps the structure sensible.

### 5B. Correct metadata

| Exercise | Field | Current | Should be | Why |
|---|---|---|---|---|
| Towel Row, Doorframe Row, Inverted Row, Banded Rows, Banded Pull-Aparts | `types` | includes `'hiit'` | drop `'hiit'` | These are pulling exercises; HIIT should mean metabolic conditioning. They flood the HIIT pool. |
